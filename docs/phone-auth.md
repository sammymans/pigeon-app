# Phone authentication and onboarding

## Deployment gate

This implementation is **not deployed or live-SMS verified**. It fails closed by default. Do not enable or deploy it without the owner's approval. No SMS credentials are included. Unit tests mock Twilio's HTTP responses; they are not evidence that a real text was delivered.

After approval, configure the intended Convex deployment (development and production are separate):

1. Create a Twilio **Verify Service**, enable SMS, and set **Code length to 6**. This is required: the application only accepts six decimal digits. Keep Verify's default ten-minute token validity, enable Fraud Guard, restrict SMS geographic permissions to supported markets, and configure spending alerts/limits. Trial accounts require verified recipient numbers and have sending restrictions. Finish any sender/region registration Twilio requires.
2. In the Convex dashboard's deployment environment variables, securely enter `TWILIO_ACCOUNT_SID` (the Twilio account's `AC…` SID), `TWILIO_AUTH_TOKEN` (its private Auth Token), and `TWILIO_VERIFY_SERVICE_SID` (the `VA…` Verify service SID). These are server-only values. Never put them in `VITE_*`, source files, command output, screenshots, or the client bundle. Use separate services/accounts for development and production.
3. Retain/configure the existing Convex Auth deployment: `JWT_PRIVATE_KEY`, `JWKS`, and `SITE_URL`; Convex provides `CONVEX_SITE_URL`. Use the Convex Auth setup procedure for the target deployment, with matching public keys and the intended frontend origin. Existing `convex/auth.config.ts` and `convex/http.ts` remain the auth configuration and HTTP routes. Do not rotate working auth keys casually: existing sessions depend on them.
4. Deploy the approved schema/functions and frontend together using the project's normal deployment workflow. Set `PHONE_AUTH_ENABLED=true` only when ready to send paid SMS. Any other value disables both sending and verification. Remove/set it false to disable this provider; existing authenticated sessions are unaffected.
5. Using an owned test phone, verify delivery, six-digit autofill/paste, incorrect and expired codes, resend after 60 seconds, consumed-code rejection, returning account login, interrupted profile completion, logout and session restoration. Verify a real newly registered user has exactly five pigeons and no invented city. Check provider errors without recording the phone/code/token. This live test remains outstanding.

Frontend configuration: `EXPO_PUBLIC_CONVEX_URL` must point at that same deployment. Set `EXPO_PUBLIC_TERMS_URL` and `EXPO_PUBLIC_PRIVACY_URL` to the owner's approved HTTPS legal documents. No documents or destinations are supplied by this change; missing destinations render non-actionable labels and a configuration notice. Native sessions use Expo SecureStore through the existing Convex Auth provider. Web sessions use the provider's browser storage; do not treat browser storage as a native keychain.

## Integration handoff

`pigeons` contains `{ ownerId: Id<'profiles'>, name: string, slot: number }`, with a `by_ownerId` index. The five slots are 0–4 in the order above. This is the single owned-pigeon inventory; it currently has no busy/flight assignment state. Messaging should extend or derive availability using these IDs instead of provisioning a competing flock. The first-letter handoff currently defaults to Mochi; messaging owns selected-bird dispatch.

`onboarding.ensureFlock({}) -> { pigeons: [{ id, name }] }` is the authenticated compatibility mutation for an **existing** profile, including a paired/demo profile. It uses the same provisioner as new onboarding, preserves every existing bird ID/name/extra slot, and inserts only absent starter slots. Concurrent calls/retries cannot duplicate grants. It never creates a profile, changes a namespace, or edits pairs. `onboarding.flock({})` is the corresponding authenticated read-only query. Messaging should ensure once before consuming inventory and subscribe to the query; no bulk migration is performed here.

`LetterApp` restores auth before displaying sign-in. Verified accounts without profiles resume profile setup; completed accounts (including existing paired-demo sessions) mount home directly. The authenticated subtree is keyed by the private `accountId` returned in status and unmounts on auth loss, so transient ready/settings/navigation state cannot leak to another account. A successful new completion shows `FlockReady`; its first-letter action mounts `Mailbox` with `initialCompose=true`, consumed only after the profile and mailbox mount, and its sky action mounts home. Returning to the app after completion goes directly home. Account-keyed drafts are never deleted by these resets. A separate messaging integration owns the deferred sender-city picker; until that lands, new profiles cannot send, and the UI/server explicitly block missing-city sends. No city is guessed or location permission requested.

Design: [Paper onboarding page](https://app.paper.design/file/01M7GFFP9QE40C6END0X03AYCB/p-9-0), file `01M7GFFP9QE40C6END0X03AYCB`, page `p-9-0`. `starter/pigeonArtwork.json` contains the original SVG exports of Mochi/Pip/Button/Noodle/Puddle (nodes `4DV-0`, `4EI-0`, `4F3-0`, `4FO-0`, `4G8-0`), not generated replacement art. Mobile browser checks use an isolated, uncommitted component harness with test callbacks; those checks prove UI behavior, not live SMS or device autofill.

Twilio references: [start verification](https://www.twilio.com/docs/verify/api/verification), [verification checks](https://www.twilio.com/docs/verify/api/verification-check), [services](https://www.twilio.com/docs/verify/api/service).

## Client contract

- `api.phoneAuth.sendCode({ phone })` is a public action. Pass an international `+` country-code number. Spaces, parentheses, dots and hyphens are removed; the result must contain 8–15 digits. It returns `{ retryAt }`, an epoch millisecond timestamp for the resend UI. Failed sends throw a safe message; they still consume rate-limit allowance because delivery can be uncertain. The UI should keep a local cooldown after an ambiguous network error as well.
- `useAuthActions().signIn('phone', { phone, code })` verifies a six-digit string and establishes the normal Convex Auth session. Leading zeros must be preserved. Sending and verification are distinct: `signIn` never sends an SMS. A successful verification needs no client-generated identity or completion flag.
- `api.onboarding.status({})` returns `{ status: 'signedOut' | 'profileRequired' | 'complete', accountId?, pigeons: [{ id, name }], username?, displayName? }`. Anonymous users without profiles are `signedOut`; existing profiles, including paired demos, bypass onboarding without changing identity. Newly verified users without a profile resume `profileRequired` on any device/session. Legacy profiles need `ensureFlock` before selected-bird sends; do not show the new-account ready screen to them.
- `api.onboarding.usernameAvailable({ username })` requires a real signed-in user and returns `{ username, available }`. Invalid syntax throws. Normalization trims, strips one leading `@`, lowercases, and requires 3–24 ASCII letters, digits, underscores or dots, with no leading dot. Availability is advisory; submit rechecks uniqueness transactionally.
- `api.onboarding.complete({ username, displayName? })` requires a verified phone for a new profile; it returns the same complete status. Optional display names are trimmed, limited to 50 Unicode code points and reject ASCII control characters. Completion creates the profile and five ordered pigeon records (Mochi, Pip, Button, Noodle, Puddle) in a single transaction. Retries return the existing profile/flock, do not rename it or duplicate records. Pigeons are inventory, not fabricated pen-pal users or social connections. Their IDs are not recipient profile IDs.

## Safety and compatibility

Convex Auth's built-in Phone provider creates a user when issuing the code, before verification. To honor creation-after-verification, this app uses the supported `ConvexCredentials` extension with provider ID `phone` and Twilio Verify. Only an approved verification response for the exact normalized phone calls Convex Auth's `createAccount`. That helper atomically reuses the same provider account and links only an existing **verified** phone; it does not trust the caller's anonymous session or merge on an unverified number. Twilio owns code generation, expiration and consumption. The app stores no OTPs and never returns Twilio response bodies or logs secrets. Keep Convex Auth verbose/debug logging disabled: library debug logs may contain account identifiers.

Private server tables hold phone identifiers and verified user metadata. No profile DTO, public sky result, onboarding result, search or pigeon record exposes a phone. Rate-limit rows are server-only, with no public read/write API. They retain a per-number counter (not a request history); establish a production retention policy before large-scale rollout.

Server mutations enforce a 60-second send cooldown, at most 5 sends per phone per hour, a deployment-wide 100 sends per day, 5 verification attempts per phone per ten minutes and 500 verification attempts per deployment per day. Windows start on the first request. Failed provider requests count. Counters persist across browsers, reloads and concurrent requests. These conservative pilot caps bound cost; a distributed attacker can exhaust the global allowance (denial of service). Before a public-scale rollout, add an edge abuse challenge/IP controls and review caps with the owner. Client timers are UX only, not security. A timed-out approved verification may require a fresh SMS because Twilio consumption and Convex session issuance cannot share a transaction.

The Password provider accepts only existing-account sign-in; new password signup is rejected before creating an account. Anonymous and demo endpoints remain for backend/demo compatibility, not promoted in the new UI. Onboarding refuses anonymous users and refuses converting demo profiles. The legacy profile save endpoint routes verified-phone accounts through the same atomic flock provisioner, so it cannot skip the grant. Pre-existing non-phone accounts retain their legacy profile setup/update behavior. Existing complete profiles remain complete without a migration or forced re-onboarding.

New profiles have **no city**. `Profile.cityId` and profile DTO `cityId` are optional; existing records remain valid. Both participants must explicitly select a city before a flight can launch. Existing `profiles.setCity` remains available outside onboarding. No location permission or guessed location is introduced.

Verification: `npx tsc -p convex --noEmit` and `npx vitest run` cover backend typing, old behavior, no pre-verification user creation, malformed/wrong/mismatched/expired code rejection, configured-service fail-closed behavior, rate caps, verified-phone linking, session-backed onboarding, username collisions, atomic retry-safe provisioning and private projections. Full browser session restoration and actual Twilio delivery require the approved configured deployment above.
